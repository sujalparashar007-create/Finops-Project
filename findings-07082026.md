## Fix 1 — Remove `finops-views` as a separate module; fold view creation into `finops-dataset`, gated by a flag

**Decision:** approved (revised from the original "genericize + rename to
`bigquery-views`" direction). `finops-views` and `finops-dataset` are
permanently coupled in practice — views always need the dataset to exist
first, and are always created together in `6-finops`. Keeping them as two
modules doesn't buy real independent reuse today, and it diverges from
CFF's own reference shape: CFF's `bigquery-dataset` module already bundles
`views`/`tables`/`materialized_views` directly inside the dataset module,
not as a separate module. Merge them to match that.

**What you're fixing:** delete `finops-views` as a standalone module.
Move view creation into `finops-dataset`, but make it **conditional** — a
caller that only wants a dataset (no views) shouldn't be forced to create
any. Gate the view resources behind an `enable_views` (or `create_views`)
flag, similar in spirit to `finops-function`'s existing `enable_function`
flag.

**Step 1 — `finops-dataset/variables.tf`:** add:
```hcl
variable "enable_views" {
  description = "If true, create the BigQuery views supplied in var.views. If false, var.views is ignored and no views are created."
  type        = bool
  default     = true
}

variable "views" {
  description = "Map of BigQuery view definitions to create when enable_views = true. Key = view/table_id, value = { friendly_name, query }."
  type = map(object({
    friendly_name = string
    query         = string
  }))
  default = {}
}
```

**Step 2 — `finops-dataset/main.tf`:** add the view resource, scoped by
`enable_views` using `for_each` over an empty map when disabled (so it's a
single conditional switch, not a `count` wrapping every view):
```hcl
resource "google_bigquery_table" "views" {
  for_each = var.enable_views ? var.views : {}

  project       = var.project_id
  dataset_id    = google_bigquery_dataset.finops.dataset_id
  table_id      = each.key
  friendly_name = each.value.friendly_name

  view {
    query          = each.value.query
    use_legacy_sql = false
  }

  deletion_protection = false

  depends_on = [google_bigquery_dataset.finops]
}
```

**Step 3 — move the SQL to `6-finops`:** the 8 FinOps queries (with their
`{source}`/`replace()` templating, the `finops_budgets_rows` computation,
and the credits-sign-convention logic) still move up into
`6-finops/finops-view-definitions.tf` exactly as before — this part of the
plan doesn't change, only where the *resource* that consumes them lives:
```hcl
locals {
  finops_view_definitions = {
    daily_cost = {
      friendly_name = "Daily Net Cost"
      query = replace(<<-EOT
        SELECT ... FROM `{source}` ...
      EOT
      , "{source}", var.billing_export_table_id)
    }
    # ...remaining 7 queries, moved as-is
  }
}
```
Update the existing `module "finops_dataset"` call in `6-finops/main.tf` to
pass the views in directly (no separate `module "finops_views"` block
anymore):
```hcl
module "finops_dataset" {
  source       = "../finops-dataset"
  project_id   = var.project_id
  dataset_id   = var.dataset_id
  location     = var.region
  enable_views = true
  views        = local.finops_view_definitions
  # ...existing iam, labels, etc.
}
```

**Step 4 — delete the `finops-views` directory** entirely (main.tf,
variables.tf, outputs.tf, versions.tf, README.md, examples/) once the
above is wired and validated — do not leave it behind as dead code.

**Step 5 — `finops-dataset/README.md` and `examples/basic`:** document the
new `enable_views`/`views` inputs, and add a views example to
`examples/basic` (a small dummy view is fine) so the module's own test
still exercises the new resource.

**Net effect:** one module (`finops-dataset`) owns both the dataset and its
views, matching CFF's shape. A caller that doesn't need views just leaves
`enable_views = false` (or omits `views`, since the default is an empty
map) and gets a plain dataset with zero extra resources. FinOps business
logic (the actual queries) still lives in `6-finops`, same as the original
plan — only the module boundary changed.

## Fix 2 — `finops-dataset`: additive IAM instead of hierarchical/authoritative

**Files:** `finops-dataset/main.tf`, `finops-dataset/variables.tf`,
`6-finops/main.tf`, `6-finops/variables.tf` (plus whichever `.tfvars`/
`locals` currently populates `dataset_iam` with real values)

**What's wrong:** the dataset IAM resource today is authoritative
(`google_bigquery_dataset_iam_binding`) — it replaces the *entire* member
list for a role on every apply, silently removing any grant made outside
this module for that same role.

**Why the variable shape is changing too:** a naive additive fix keeps
`var.iam` as `map(list(string))` and flattens it into role/member pairs
with a nested `for` inside `flatten([...])`. That's a nested-loop pattern,
which `agents.md` explicitly disallows: *"No nested loops or multi-level
conditional nesting — if the logic needs that, restructure the input
variable shape instead."* So restructure `var.iam` into a flat list of
role/member objects instead of fixing it with a flatten — this removes the
nested loop entirely, not just the authoritative-vs-additive issue.

**Step 1 — `finops-dataset/variables.tf`:** change the `iam` variable's
type from `map(list(string))` to a flat list of objects:
```hcl
variable "iam" {
  description = "List of role/member grants. Each entry is one role assigned to one member."
  type = list(object({
    role   = string
    member = string
  }))
  default = []
}
```

**Step 2 — `finops-dataset/main.tf`:** replace
`google_bigquery_dataset_iam_binding` with the additive
`google_bigquery_dataset_iam_member`, `for_each` directly over the new list
— no flatten, no nested loop:
```hcl
resource "google_bigquery_dataset_iam_member" "bindings" {
  for_each = { for entry in var.iam : "${entry.role}/${entry.member}" => entry }

  project    = var.project_id
  dataset_id = google_bigquery_dataset.finops.dataset_id
  role       = each.value.role
  member     = each.value.member
}
```
Update the existing comment above this resource to describe additive
behavior instead of the old authoritative rationale.

**Step 3 — update the caller, `6-finops` (this is a required, two-place
change, not optional):** `6-finops/variables.tf` declares its own
`dataset_iam` variable with the same type as `finops-dataset`'s `iam`, and
passes it straight through in `6-finops/main.tf` (`iam = var.dataset_iam`).
Since `finops-dataset` doesn't output any IAM data (only `dataset_id`,
`project_id`, `dataset_full_id` — checked, no downstream type dependency
beyond this one wire), the only place the type must be kept in sync is
here:
```hcl
# 6-finops/variables.tf
variable "dataset_iam" {
  description = "List of role/member grants for the FinOps BigQuery dataset."
  type = list(object({
    role   = string
    member = string
  }))
  default = []
}
```
`6-finops/main.tf`'s `iam = var.dataset_iam` line itself does not need to
change — only the type declaration above it.

**Step 4 — update real values:** find wherever `dataset_iam` is currently
populated with actual role/member data (a `.tfvars` file or a `locals`
block in `6-finops`) and convert its literal syntax from the old
map-of-lists shape:
```hcl
dataset_iam = {
  "roles/bigquery.dataViewer" = ["group:finops-team@example.com"]
  "roles/bigquery.dataEditor" = ["serviceAccount:etl-sa@..."]
}
```
to the new flat list-of-objects shape:
```hcl
dataset_iam = [
  { role = "roles/bigquery.dataViewer", member = "group:finops-team@example.com" },
  { role = "roles/bigquery.dataEditor", member = "serviceAccount:etl-sa@..." },
]
```

**Note on ordering:** do Steps 1–2 (`finops-dataset`) and Steps 3–4
(`6-finops`) together, in the same change/PR — do not merge the module
change alone, since `terraform plan` in `6-finops` will fail immediately
with a type-mismatch error on the `iam = var.dataset_iam` line until the
caller's variable type and its real values are updated to match.

## Fix 3 — `finops-budgets`: generic `budget_filter` + document `spend_basis` as an input

**Files:** `finops-budgets/main.tf`, `finops-budgets/variables.tf`,
`finops-budgets/README.md`

**What's wrong:** `budget_filter` only exposes `projects`,
`credit_types_treatment`, `calendar_period` today. GCP's
`google_billing_budget.budget_filter` block also supports
`resource_ancestors`, `labels`, and `services` — none of which a caller can
currently set. Also, `spend_basis` already exists as an input on
`threshold_rules`, but it isn't documented as a caller-settable input in
the README — fix that gap too.

**Change in `main.tf`:**
```hcl
budget_filter {
  projects               = try(each.value.budget_filter.projects, null)
  resource_ancestors      = try(each.value.budget_filter.resource_ancestors, null)
  labels                  = try(each.value.budget_filter.labels, null)
  services                = try(each.value.budget_filter.services, null)
  credit_types_treatment  = try(each.value.credit_types_treatment, "INCLUDE_ALL_CREDITS")
  calendar_period         = try(each.value.calendar_period, "MONTH")
}
```

**Change in `variables.tf`:** add a nested `budget_filter` object to the
`budgets` variable's type:
```hcl
budget_filter = optional(object({
  projects           = optional(list(string))
  resource_ancestors = optional(list(string))
  labels             = optional(map(string))
  services           = optional(list(string))
}))
```

**Change in `README.md`:** add `spend_basis` (values: `CURRENT_SPEND`,
`FORECASTED_SPEND`) to the documented list of caller-settable fields on
`threshold_rules`, and document the new `budget_filter` object's fields
above.

## Fix 4 & 5 — `finops-function`: remove `allUsers` invoker, add dedicated runtime SA

**File:** `finops-function/main.tf`, `finops-function/variables.tf`

**What's wrong (Fix 4, High severity):**
```hcl
resource "google_cloud_run_service_iam_member" "pubsub_invoker" {
  project  = var.project_id
  location = var.region
  service  = var.function_name
  role     = "roles/run.invoker"
  member   = "allUsers"
}
```
This makes the Cloud Run service backing the function publicly invokable
over HTTP by anyone — unnecessary for a 2nd-gen Eventarc/Pub/Sub trigger.

**Fix:** scope the grant to the actual Eventarc trigger's service account
instead of `allUsers`:
```hcl
resource "google_cloud_run_service_iam_member" "eventarc_invoker" {
  project  = var.project_id
  location = var.region
  service  = var.function_name
  role     = "roles/run.invoker"
  member   = "serviceAccount:${var.eventarc_trigger_service_account}"
}
```
This requires exposing `event_trigger.service_account_email` as a variable
(currently unset on the trigger, so it defaults to the Compute Engine
default SA) and referencing that same SA in the invoker grant above — add:
```hcl
variable "eventarc_trigger_service_account" {
  description = "Service account used by the Eventarc trigger; also granted roles/run.invoker on the Cloud Run service."
  type        = string
}
```
and set `event_trigger.service_account_email = var.eventarc_trigger_service_account`
in the `google_cloudfunctions2_function` resource's `event_trigger` block.

**What's wrong (Fix 5, Medium severity):**
```hcl
locals {
  service_account_email = var.service_account_email != "" ? var.service_account_email : "tf-executor@${var.project_id}.iam.gserviceaccount.com"
}
```
Defaults the function's own runtime identity to the shared Terraform
deploy SA (`tf-executor`) — a least-privilege violation.

**Fix — CFF-style dedicated-SA creation path:**
```hcl
variable "create_service_account" {
  description = "If true, this module creates a dedicated runtime service account instead of requiring one via service_account_email."
  type        = bool
  default     = true
}
```
```hcl
resource "google_service_account" "function_runtime" {
  count        = var.create_service_account ? 1 : 0
  project      = var.project_id
  account_id   = "${var.function_name}-sa"
  display_name = "Runtime SA for ${var.function_name} (finops-function module)"
}
```
```hcl
locals {
  service_account_email = (
    var.create_service_account
    ? google_service_account.function_runtime[0].email
    : var.service_account_email
  )
}
```
No change needed to `google_secret_manager_secret_iam_member.accessor` —
it already references `local.service_account_email` correctly.

**Note:** Fix 8 below later replaces this exact
`create_service_account`/`service_account_email` pair with a single
null-sentinel variable. Implement Fix 5 as written here first (this is the
form specified for this fix), then apply Fix 8's conversion afterward in
the same module — do not skip straight to the null-sentinel form, since
Fix 8 depends on this working version existing first.

## Fix 6 — `finops-function` and `finops-alerts`: additive member-permission resource for user access

**Files:** `finops-function/main.tf`, `finops-function/variables.tf`,
`finops-alerts/main.tf`, `finops-alerts/variables.tf`

**What you're adding:** today, only the function's own runtime SA (or
alerts' own resources) get IAM grants — there's no way for a human/team to
be granted access to either module's resources. Add an explicit, additive
IAM input to both modules, following the same shape as `finops-dataset`'s
now-additive `iam` variable from Fix 2.

**`finops-function`:**
```hcl
variable "secret_accessors" {
  description = "Additional members (besides the runtime SA) granted secretAccessor on this function's secrets."
  type        = list(string)
  default     = []
}
```
Extend the existing `google_secret_manager_secret_iam_member.accessor`'s
`for_each` to include both the runtime SA and every member in
`var.secret_accessors` (flatten into secret/member pairs the same way Fix 2
flattens role/member pairs).

**`finops-alerts`:**
```hcl
variable "iam" {
  description = "Additional IAM grants on this module's Pub/Sub topic and notification channels. Key = role, value = list of members."
  type        = map(list(string))
  default     = {}
}
```
Add a new additive resource (`google_pubsub_topic_iam_member`, one per
role/member pair, same flatten pattern as Fix 2) scoped to
`google_pubsub_topic.budget_alerts.id`.

Both additions are additive-only (`_iam_member`, never `_iam_binding`) —
consistent with Fix 2's direction for the whole repo.

## Fix 8 — Standardize "create new or use existing" flags to the null-sentinel pattern

**Pattern to use everywhere below** — one nullable variable, not a bool +
fallback string pair:
```hcl
variable "existing_<resource>_id" {
  type    = string
  default = null
}
locals {
  create_<resource> = var.existing_<resource>_id == null
}
# used as: count = local.create_<resource> ? 1 : 0
```
Reference already proven in production:
`terraform-azurerm-aks/variables.tf` → `nat_gateway_id` (and
`route_table_name`), both `default = null`, both drive
`count = var.x == null ? 1 : 0` downstream in `modules/cluster/main.tf`.

**1. `finops-function`:**
- Replace the `create_service_account` / `service_account_email` pair
  (built in Fix 5) with a single `existing_service_account_email = null`
  variable. When null, create the dedicated SA (as in Fix 5); when set,
  use it directly as the runtime SA email — no separate bool needed
  anymore.
- Add `secret_config { existing_secret_ids = null }`-equivalent: expose
  `existing_secret_ids` (map, default `{}` — use empty map, not null, since
  this is a per-key map not a single ID) so a caller can supply
  already-existing secret IDs for some or all keys in
  `var.secret_environment`; skip creating a `google_secret_manager_secret`
  for any key present in `existing_secret_ids`.

**2. `finops-dataset`:**
- Add `existing_dataset_id = null`. When null, create
  `google_bigquery_dataset.finops` as today; when set, skip creation and
  reference `var.existing_dataset_id` in the IAM resource from Fix 2 and in
  `outputs.tf`.

**3. `finops-budgets`:**
- First confirm whether this module actually creates its own Pub/Sub
  topic. As it stands, `pubsub_topic_id` is consumed as an input-only
  variable (default `""`) with no `google_pubsub_topic` resource in this
  module — if that's confirmed, this flag belongs in `finops-alerts`
  instead (below), not here. Do not add topic-creation logic to
  `finops-budgets` just to make this flag apply to it.

**4. `finops-alerts`:**
- Add `existing_topic_id = null` for `google_pubsub_topic.budget_alerts` —
  skip creation when set, reference `var.existing_topic_id` downstream.
- Add `existing_notification_channel_ids = null`-equivalent: since this is
  a per-email map (not a single ID), use
  `existing_notification_channel_ids = {}` (map default, not null) — for
  any email present in this map, skip creating
  `google_monitoring_notification_channel.email` for that email and use
  the supplied channel ID instead.

**Execution note:** do Fix 5 first in `finops-function`, confirm it works,
then apply this fix's conversion on top of it in the same module — do not
implement Fix 5 and Fix 8 as a single combined change.

## Fix 10 — Final README audit: encoding, formatting, and content-match check

**Decision:** approved, do this last — after Fix 9's renaming, so READMEs
are checked in their final post-rename state, not before.

**Scope:** every module's `README.md` touched by any fix above
(`finops-reporting-dataset` [formerly `finops-dataset`], `finops-budgets`,
`finops-alerts`, `finops-function`, `finops-firewall-policy` [formerly
`hierarchical-policy`], `project-bootstrap` [formerly `project`],
`finops-foundation`, `6-finops`) — do not skip modules that had no direct
code fix above; check all of them, since renaming (Fix 9) alone can leave
stale references behind even in unfixed modules if they mention a renamed
module by name (e.g. `finops-foundation`'s README may reference
`project`/`hierarchical-policy` by their old names in a usage note).

**What to check, per README:**
1. **Corrupted/mojibake characters** — this repo has a recurring pattern of
   em-dash (`—`) corruption showing up as `â€"` or the U+FFFD replacement
   character (`�`), already confirmed present in multiple modules this
   session (`finops-alerts/main.tf`, `finops-function/outputs.tf` header
   comments, `finops-dataset/README.md`'s arrow typo). Open each README and
   scan byte-level for these patterns — fix any found by replacing with a
   correct `-` or `—` as appropriate to the sentence.
2. **Formatting consistency** — confirm each README follows the same
   structure already established across this repo's other module READMEs
   (purpose statement, inputs table, outputs table, minimal usage example,
   per `agents.md`'s checklist: *"README.md written: purpose, inputs,
   outputs, minimal usage example"*). Flag (don't silently reformat) any
   README that's missing one of these sections entirely.
3. **Content matches current code** — for every variable/output documented
   in the README, confirm it still exists with the same name/type/default
   in the module's actual `variables.tf`/`outputs.tf` after all fixes above
   have landed. This specifically means re-checking:
   - `finops-reporting-dataset`'s README reflects the new `iam` type
     (`list(object({role, member}))`, not the old `map(list(string))`),
     the new `enable_views`/`views` inputs, and no longer describes itself

   - `finops-function`'s README reflects `create_service_account`,
     `existing_service_account_email`, `existing_secret_ids`,
     `secret_accessors`, and `eventarc_trigger_service_account` (all added

     `service_account_email`-only fallback-to-`tf-executor` behavior.

     `existing_notification_channel_ids` inputs (per Fixes 6, 8).
   - `finops-dataset`'s example usage block in its README no longer shows

4. **Syntax issues in code blocks** — any HCL example inside a README
   should be copy-paste-valid Terraform (correct brace matching, no leftover
   placeholder text, no stale variable names) — run a visual check on each
   fenced code block, not just prose.

**How to report findings:** do not silently fix content mismatches found
under point 3 without listing them — add a short "README audit" note to
each module's PR description listing what was found/corrected, since a
content mismatch there may indicate the code fix itself was incomplete,
not just a docs gap.
